# TRD 通用质量评审维度

> 来源：基于团队积累的 TRD 质量分析数据提炼的 8 个核心评审维度。

---

## 评审维度总览

| 维度 | 说明 | 权重 |
|------|------|------|
| 接口定义完整性 | 是否有完整的 proto/字段定义、HTTP method+path、请求/响应示例、错误码 | HIGH |
| 业务规则清晰度 | 业务逻辑是否明确，无歧义 TBD、无"待确认"占位 | HIGH |
| 边界与异常处理 | 是否覆盖边界值、异常路径、并发场景、降级策略 | HIGH |
| 数据结构清晰度 | DB DDL、Kafka schema、状态机、字段类型约束是否完整 | HIGH |
| 安全与合规 | 日志脱敏、鉴权设计、PII 保护、密钥管理是否有说明 | MEDIUM |
| 非功能性需求（NFR） | SLA/P99/QPS、监控告警阈值、性能预算是否定义 | MEDIUM |
| 可测试性 | 是否有验收标准、测试场景、上线 checklist、测试数据 | MEDIUM |
| 工程化完整性 | 灰度方案、回滚 SOP、部署顺序、配置说明是否完整 | MEDIUM |

---

## 评分规则（10 分制）

每个维度 0-10 分：
- **10 分**：完美覆盖，方案合理且有最佳实践示例
- **8-9 分**：完整覆盖，个别细节可改进
- **6-7 分**：基本覆盖，有明显缺失但核心路径有
- **4-5 分**：部分覆盖，关键信息缺失较多
- **2-3 分**：仅提及但不完整
- **0-1 分**：完全未涉及

综合评分 = 各维度加权平均（HIGH 权重 × 1.5, MEDIUM 权重 × 1.0）

## 写得好的标准（参考基准）

### 1. 背景与目标
- 明确说明问题根因、解决目标、设计决策依据
- 提供版本差异对比表（如 V1→V2 变化清单）
- 给出业务原则，并以 quote 形式前置声明

### 2. 架构设计
- 提供系统架构图（服务依赖、数据流转、调用链路）
- 明确服务边界和职责分工
- 说明关键组件选型理由（如为什么用 Kafka 而非 RPC）

### 3. 接口定义（核心维度，权重最高）
- **HTTP 接口**：完整 method + path + request params + response fields + error codes
- **gRPC 接口**：完整 proto 定义（字段名/类型/必填/枚举值）
- **WebSocket**：topic 命名、payload 结构、推送触发条件
- **Kafka**：topic 名称、消息 schema（字段/类型/必填）、消费者组策略
- 提供真实请求/响应示例（JSON 格式）
- 错误码字典完整，区分业务错误和系统错误

### 4. 数据库设计
- 完整 DDL（含字段注释、类型、默认值、NOT NULL、索引）
- 说明分表策略、乐观锁、幂等键设计
- 新旧版本变更对比（ALTER TABLE vs CREATE TABLE）
- 历史数据兼容策略（哪些表补全、哪些不补全）

### 5. 状态机与业务流程
- 完整状态枚举（包含所有中间态和终态）
- 状态转换条件明确（触发事件、前置条件、优先级）
- 异步流程的最终一致性保证说明

### 6. 异常处理
- 枚举所有异常场景（RPC 超时、空值、网络分区、并发冲突等）
- 每种异常的处理策略（fail-open/fail-close、重试次数、退避策略）
- 降级机制（feature flag、熔断、服务降级）
- 幂等设计（Redis key 格式和 TTL）

### 7. 安全与合规
- 日志脱敏规则（哪些字段不能打印）
- SQL 注入防护方式（参数化查询等）
- 鉴权方式（token + user_id 二次校验、签名机制等）
- PII 数据处理（不含 PII 字段、加密传输、合规站差异）
- 密钥管理（不明文存储、环境变量替代硬编码）

### 8. 非功能性需求
- 性能基线（峰值 QPS、P99 延迟、SLA）
- 监控指标（指标名、告警阈值、告警接收人）
- 容量规划（新增调用对下游服务的压力评估）

### 9. 可测试性
- 内置测试场景（含预期结果）
- 测试数据清单（测试账号、配置参数）
- 上线验收 checklist（可量化的验证标准）
- 明确前向兼容性（哪些路径不受改动影响）

### 10. 工程化
- 灰度方案（白名单/百分比、切换逻辑、观察期）
- 回滚 SOP（每项改动的回滚步骤和判定阈值）
- 部署顺序约束（下游先上线、数据迁移先行等）
- 配置说明（Nacos key、默认值、热更新策略）

## 写得差的反模式（常见问题）

### 1. 接口契约缺失（高频问题）
- 只有功能描述，无字段定义（类型、必填性、枚举值）
- 接口路径不完整（只有方法名，无完整 HTTP method + URL）
- 响应字段结构缺失（无示例 JSON，无字段说明）
- 错误码未定义或"TBD"占位
- Kafka 消息只有描述，无 schema 定义

### 2. 业务规则模糊
- 关键字段默认值有矛盾（DDL DEFAULT 与文档说明不一致）
- 预期结果包含"或者"（歧义，测试无法判断正确）
- "待确认"、"待产品对齐"等占位导致规则不完整
- 命名不一致（同一概念在文档不同位置使用不同名称）

### 3. 边界条件缺失
- 无边界值范围定义（字段最大值、精度规范）
- 并发场景未说明（双过风险、分布式锁策略）
- 多账户/子账号等特殊用户场景未覆盖
- 中间态失败后的补偿逻辑未定义

### 4. 安全盲区
- 密钥/token 明文提交或出现在日志中
- 未说明 PII 字段的传输加密和存储加密方案
- 无安全自检章节（OWASP 类检查项）

### 5. NFR 空白
- 无性能 SLA（可接受延迟上限）
- 无监控指标定义
- 无容量评估（新调用对现有系统的 QPS 影响）

### 6. 文档形式问题
- 以会议记录/CR 报告代替正式 TRD
- 缺乏系统架构图、数据流图
- 存在未清理的 TODO 注释

### 7. 历史数据兼容性缺失
- 新字段上线后历史数据如何处理（空值、默认值、迁移脚本）
- 老版本 App/前端如何兼容新字段（强升级 vs 兼容窗口）

### 8. 缺少回滚方案
- 无紧急回滚 SOP
- 无功能开关（feature flag）支持动态关闭
- 无回滚后对已处理数据的处置说明

      "issues": [
        {
          "severity": "high",
          "description": "...",

          "suggestion": "..."
        }
      ]
    }
  ],

  "summary": "一句话总结"
}
