# TRD 监控覆盖评审维度

> 来源：从 monitor-coverage-eval skill 提取的 TRD 评审相关部分。
> 本模块仅基于 TRD 文档内容评估监控告警设计的完整性，不依赖 alarm MCP 工具。

---

## 评审目标

从 TRD 中抽取所有可监控组件（接口、Kafka、Cron、DB、Redis、下游依赖），对照标准映射表检查：
1. 是否有监控/告警相关说明
2. 覆盖维度是否完整
3. 告警阈值和通知策略是否合理

---

## 组件类型 × 必带监控维度

| 组件类型 | 必带维度 |
|---|---|
| **同步 HTTP/RPC 入口** | QPS / 错误率 / P99 / P999 / 限流触发率 / 5xx 数量 |
| **异步消费（Kafka/MQ）** | lag / 消费错误率 / 消费 RT / DLQ 堆积 / 消费进度回退 |
| **Cron 任务** | 未触发告警（连续 N 周期未跑）/ 执行失败 / 执行超时 / 漏跑次数 |
| **DB 依赖** | 慢查询（P99 + 绝对阈值）/ 连接池满 / 错误率 / QPS 异常波动 |
| **Redis 依赖** | 慢请求 / OPS 异常 / 连接错误 / 大 key 告警 |
| **下游 RPC 依赖** | 错误率 / P99 / 熔断触发 / 限流触发 |

---

## 资金链路服务额外维度

若 TRD 涉及资金操作（划转、上账、下账、充值、提现等），必须额外检查：

| 维度 | 阈值建议 | 优先级 |
|---|---|---|
| 资金差异告警 | 单笔变动 >5% 必告警 | P0 |
| 对账告警 | 差异笔数/金额 | P0 |
| 余额突变告警 | 对比 5 分钟窗口 | P0 |
| 业务量突降告警 | 同比下降 >50% | P1 |
| 关键规则通知 | voice=1 电话 + 短信 + Oncall (备份 ≥3 人) | P0 |

---

## Kafka 阈值区分

| 维度 | 资金类 Topic | 其他 Topic |
|---|---|---|
| 消费延迟（lag） | >1min 即告警 P0 | >5min 告警 P1 |
| 消费积压 | 非零即告警 P0 | 超阈值告警 P1 |
| 消费错误率 | >1% P0 | >5% P1 |

---

## FMEA 故障模式检查（从 TRD 可判定的部分）

以下故障模式可以直接从 TRD 内容判断是否有覆盖：

| 故障模式 | TRD 中应有的说明 | 缺失时的风险 |
|---|---|---|
| **状态卡死** | 状态机所有非终态的超时告警设计 | 订单/任务永远卡在中间态无人感知 |
| **业务错误码未告警** | 错误码表中每个码的监控覆盖说明 | 业务错误发生时无法及时发现 |
| **回滚/补偿失败** | 补偿失败的告警方案 | SAGA 失败后无人处理 |
| **重试不幂等** | 重试次数/幂等键冲突的监控 | 重复扣款/重复发放 |
| **下游超时未降级** | 熔断/降级触发的告警 | 雪崩时无法快速感知 |
| **批次漏算/漏跑** | Cron 心跳/批次完整性检查 | 派息/结算漏处理 |

---

## 通知策略检查

| 检查项 | 合格标准 |
|---|---|
| 告警分级 | 有明确的 P0/P1/P2 分级 |
| 通知渠道 | P0 至少电话+短信+IM；P1 至少 IM+短信 |
| 值班人 | 有明确的 Oncall 负责人或轮值策略 |
| 备份人 | P0 告警至少有 1 个 backupHandler |
| 升级策略 | 超时未 ACK 的升级机制 |
