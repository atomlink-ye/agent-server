# 0012. MCP dispatch and confirmation is the RunTrace backbone

- Status: Accepted
- Date: 2026-08-12

## Context

`GET /api/v1/works/:workId/runs/:workRunId/trace` was supposed to answer five
questions about a round of work: what happened at each step, which task it
belonged to, when each agent started and finished, what each agent's task was,
and how it turned out.

It could not. `events[]` carried only a `type` and a timestamp, so a reader could
see that _something_ happened but not _what_. Worse, every result and payload
came back as `not_present` or `redacted`, so the fifth question — how did it turn
out — had no answer at all.

The reason those fields were empty is not an oversight. Execution output is free
text produced by a provider under prompt influence. Persisting it verbatim would
push provider-controlled strings into durable state and into public responses;
`safeRuntimeToolNamePayload` deliberately strips anything outside a small
whitelist. Any design that tries to make the timeline richer by capturing more of
that free text is arguing to weaken that boundary.

There is a second class of facts in the same system that has none of those
problems: the MCP calls the platform itself dispatches and confirms. Those are
schema-bound, generated by us, and carry a canonical tool name from our own
catalog. They are safe to show without redaction.

## Decision

**The RunTrace timeline is built from MCP dispatch and confirmation. Execution
detail lives in the Chat Detail, reached by an explicit pointer.**

Four constraints make this honest rather than merely convenient:

1. **The response states its own coverage.** A top-level `timeline_coverage`
   carries `scope: 'mcp_dispatch_and_confirmation'`, `completeness: 'mcp_only'`,
   and an explicit `excluded_execution` list (`direct_shell`, `direct_file_edit`,
   `other_non_mcp_execution`). Work an agent does without going through MCP
   leaves no record here, and the interface says so rather than letting a caller
   assume full coverage.
2. **MCP return values still go through `capture_status`.** The timeline reports
   whether a response was observed; it never inlines the body.
3. **The Chat Detail pointer is a first-class field**, not something the caller
   assembles. Each activity carries `chat_detail.method` and `chat_detail.path`
   with IDs already filled in.
4. **The two layers join deterministically.** `chat_detail.target` carries
   `run_id`, `sequence`, and `activity_id`, so a timeline entry resolves to one
   specific position in the chat detail — not "go look in that conversation".

The security whitelist is not widened. Scattered string literals were replaced
with references to `AGENT_SERVER_CANONICAL_TEAM_MCP_NAMES`, so the whitelist
itself becomes the single source of truth for which names may be persisted.

`capture_status: 'complete'` is renamed to
`projection_status: 'internally_anchored'`. `complete` only ever promised that
the identity collections and the two remediation descriptors were present and
internally anchored — it never promised that the facts omitted by the follow-up
endpoints had been captured. With an additional explicitly-uncovered region now
declared, `complete` would read as "I got everything".

## Consequences

`status` and `result_capture_status` are independent. `status` reflects the MCP
call lifecycle; `result_capture_status` derives from whether the provider event
actually carried a return field. A `completed` call whose response was never
observed is a real and expected state, and callers must not infer one from the
other.

The timeline is honest about a blind spot rather than pretending to be complete.
Anything a caller needs about non-MCP execution has to come from the Chat Detail,
and the interface points them there.

No migration was needed: the existing `run_events.payload` JSONB carries the new
structured lifecycle facts.

Because the timeline's usefulness now rests on the capture chain staying alive,
the smoke suite asserts both that at least one activity reports `redacted` and
that the status counts sum to the activity count. A widened-but-vacuous assertion
here is indistinguishable from having no test: breaking the write path entirely
must fail the suite, and mutation testing confirms it does.
